# Coming from TanStack Router

The names mostly transfer: `beforeLoad` is `beforeLoad`, route-level `pendingComponent`/`errorComponent` exist, search is validated by a schema, blockers and scroll restoration exist under near-identical names. What does not transfer is the shape around the names: TanStack Router composes a nested route tree whose levels render each other through outlets, and caches loader results; here the route is the page — a table with layouts, a stack of resolved view snapshots, and loaders that only run when the resolution actually changes. The map below is written against this package's source; the TanStack side is its current documentation at [tanstack.com/router](https://tanstack.com/router/latest/docs/framework/react/overview).

For why the differences are structural rather than cosmetic — back with zero requests, a search change that runs nothing, the blocker rewind, view-transition timing — see [Structural differences vs TanStack Router](../README.md#structural-differences-vs-tanstack-router) in the README.

## Concept map

| TanStack Router | here | note |
| --- | --- | --- |
| `createRootRoute` + `createRoute({getParentRoute, path})` + `addChildren` — or the file-based route generator | one route literal passed to `createRoutes()` | `createRoutes` is an identity function with `satisfies` semantics: the table is checked against `Route` while every `path` keeps its string-literal type (a `const` modifier on the parameter), which is what makes `RoutePaths<typeof routes>` possible. `children` nest for *matching* — a level matches a path prefix — composition follows the match (one `<View />` slot per level, see below), not the other way round. |
| router `context` (`createRootRouteWithContext`, merged with what each `beforeLoad` returns) | `context` prop on the Router components, or the `context` option on `createRouter` | One synchronous value per router instance, handed to every `data` loader and `beforeLoad` guard as `ctx.context`. Type it through `Route`'s third generic — `Route<'/list', Search, AppContext>` — or by annotating the callback; the prop's type is inferred into `router.context`. |
| `beforeLoad` | `beforeLoad` | Same name, same semantics: runs shallow → deep before the level's loader; a failing level skips its loader and its descendants. Redirect by *returning a path string* (TanStack: return or throw a `redirect()` object); more than 10 chained redirects reject with `RedirectLoopError`. |
| `loader` + `useLoaderData({from})` | route `data` + `useData<T>()` | The read is path-agnostic by design — no `from` route id; `useData<RouteDataOf<typeof loadX>>()` derives the annotation from the loader itself. Why the `from` shape was rejected is documented in the README's "Typing `useData`" section. |
| `validateSearch` + `useSearch({from})` | route `search` — any [Standard Schema](https://standardschema.dev) (zod/valibot/arktype) — plus `useSearch(schema)` | Parsed at resolve time; loaders and guards receive a typed `ctx.search`, an invalid search fails the level through the error layers. `useSearch(schema?)` degrades to the raw string-keyed object without a schema; both flavors subscribe to history and re-render on every location change. `useSetSearch(schema)` is the validating setter twin — it throws `SearchError` without touching the location. |
| `loaderDeps` — a cache *key*: deps changed → the route reloads; unchanged → stale-while-revalidate | `searchDeps` — a skip *list*: every level declared and no projection changed → the current view snapshot is re-committed, zero guards/loaders/imports | Opposite polarity applied to the same problem. Chain coverage is all-or-nothing (one undeclared level = resolve on every navigation, byte for byte), and keys the `search` schema validates strictly must be declared — the fast path runs no schema. |
| `pendingComponent` + `pendingMs` — shown once a load has been pending past the threshold (default 1s), in-app navigation included | route `pendingComponent` | Renders ONLY when there is no previous view to retain — cold start, refresh, re-navigation after an error; the nearest matched ancestor's wins. In-app navigation keeps the previous view, and the global loading signal (`useLoading`) covers that phase instead. |
| `errorComponent`, falling back to `parentRoute.errorComponent`, then `defaultErrorComponent` | route `errorComponent`, falling back to the router-level `errorHandler` | Covers resolve-phase failures (loader/guard/search — no `ctx.phase`) AND render-phase throws (`ctx.phase === 'render'`): every level's resolved view is wrapped in a route-level error boundary, so a rendering crash never escapes past its route. |
| `useBlocker({shouldBlockFn, withResolver, enableBeforeUnload})` → `{status, proceed, reset}` | `useBlocker(fn)` → `{state, proceed, reset}` | Predicate polarity reversed: `shouldBlockFn` returning `true` blocks; here returning `true` allows (an allow-list — invert your dirtiness check). Ours is synchronous and fail-closed (a throw counts as a veto); a vetoed browser POP is automatically pushed back — the rewind is in the library; `proceed()` bypasses only this hook's own blocker, strictly one-shot, and retries as a fresh push navigation. |
| `<Link to params search>` — typed by default from the route tree | plain `Link` is untyped; `<TypedLink<RoutePaths<typeof routes>> to params>` opts in | Give `TypedLink<typeof routes>` the whole table and `search` joins the discrimination, typed by the pattern's schema input. Runtime backstop: click-time interpolation; a missing required param throws instead of navigating. `TypedNavLink`/`TypedPrefetchLink` bring the same narrowing to the active-state and prefetching links. |
| `scrollRestoration: true` router option (the `<ScrollRestoration />` component is deprecated there); `useElementScrollRestoration` for manual cases | `<ScrollRestoration />` placed inside the Router | Restores the scroll offset per history entry on back/forward and resets on push (`resetOnPush={false}` to keep). Save and restore are sequenced around view commits, so it stays correct while a view transition is open. |
| `viewTransition` per navigation / `defaultViewTransition` router-wide; `ViewTransitionOptions.types` computed from `{fromLocation, toLocation, pathChanged, …}` | `viewTransition` prop on the Router components | `true` animates pushes only — a pop lands on a view-stack snapshot; a predicate decides per navigation on `{action, to, from}`; the direction maps to transition types for you (`:active-view-transition-type(push\|pop)`); commits are gated behind the transition callback. The animated scope is your CSS in both routers. |

## Flat table vs nested routes — the mental migration

TanStack Router builds a route *tree*: every route is created against a parent, matched levels render top-down, and each level's component renders the next through `<Outlet />`. Layouts are parent routes, pathless layouts are `id` routes, and the URL structure and the component tree share one shape.

Here the stance is **the route is the page**. The table is conceptually flat — each row is a full page with a `path`, a lazy `component` and an optional `data` loader. Nesting exists, but only for matching and sharing: a route without `path` is a layout whose children match the remaining path, and `View` renders the whole matched chain — each level's component wraps the next through `<View />`, one view slot per level. There is no per-level outlet choice and no parallel routes.

When migrating:

- A TanStack **layout route** — chrome shared by a URL subtree: navigation, footer, data every page under it needs — becomes a layout level: the top object with `component` and `children` but no `path`, rendering `<View />` where the page goes.
- A TanStack **nested route that exists for composition** — tabs inside a page, a master-detail pane, a dialog — does not become a route. A URL fragment whose state you want to keep is a *component in the page*, plus optionally search params; child routes are for fragments where a distinct URL should land on a distinct full page with its own lifecycle.
- Index and fallback: a leaf child with `path: ''` matches whatever is left under its parent, serving as the parent's index route and as the fallback for paths unmatched under the parent — siblings that match with real segments outrank it by specificity, so its declaration position no longer decides.
- Matching itself is leaner: every matching chain is collected and the **most specific one wins** — per segment, static text outranks a dynamic `:param`, which outranks a splat `*wildcard`, and every segment adds to the chain's score so longer chains outrank shorter ones; **declaration order only breaks ties** between equally specific chains. A parent whose prefix matched but whose children all failed never hides later siblings. Trailing slashes are significant (`/users/` does not match `/users`), matching is case-sensitive, and params of nested levels merge deep over shallow.

## Deliberately not built

- **File-based routing** — route generation and file conventions are a build step around the same data. Here the table is plain data and code splitting is a lazy `component: () => import('./View')` per level: no generator, no generated route tree to keep typed.
- **Nested/parallel routes** — the route is the page; a URL fragment with independent state is a component, not a child route (see above).
- **Deferred data / `<Await>`** — loaders here never return un-awaited promises and views commit whole. The same effect composes from standard pieces: secondary data rides the component channel (non-blocking, loading state where the data renders), and the `<Await>` ergonomics are a `<Suspense>` boundary plus react-toolroom's `useSuspenseResult` handing React the in-flight result. See [Deferred data without `<Await>`](../README.md#deferred-data-without-await) in the README; painless is the living reference for both channels.
- **SSR framework integration** — no server framework is bundled, but the data capability is in the library: `resolveViewServer`/`createHydrateResolveView` (`src/resolve-view.tsx`) resolve the matched chain with its data on the server, `resolveServerView` (`@native-router/react/server`) renders the view plus an inline data payload, and `hydrate` (`@native-router/react/ssr`) reuses that payload on the client with zero refetch. A template that ships as a static SPA (painless does) simply never calls it — the capability lives in the library, unused.
